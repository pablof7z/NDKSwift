# Audit: Relay / Subscription / RPC

Scope: `Sources/NDKSwiftCore/Relay/`, `Sources/NDKSwiftCore/Subscription/`, `Sources/NDKSwiftCore/Core/Subscription/`, `Sources/NDKSwiftCore/RPC/`, `Sources/NDKSwiftCore/RelayIntelligence/`, and the relay-flow integration parts of `Core/SignatureVerification/`.

The audit examined ~25 files plus their callers; below are the high-signal findings.

## Critical (correctness bugs)

- **NIP-01 `CLOSED` message is never parsed; all CLOSED handlers are dead code.** — `Sources/NDKSwiftCore/Relay/NostrMessage.swift:1-16, 42-176` — `NostrMessageType` and `NostrMessage` do not declare a `closed` case, and `parse(from:)` will throw `parseError` ("Unknown message type") whenever a relay sends `["CLOSED", subId, reason]`. The error is then swallowed silently by `NDKRelayConnection.handleReceivedMessage` (`Relay/NDKRelayConnection.swift:466-469` — `NDKNetworkLogger.logNetworkParseError` only logs). Consequently `NDKRelaySubscriptionManager.routeClosed` (`Relay/NDKRelaySubscriptionManager.swift:133-140`), `NDKRelaySubscription.handleClosed` (`Relay/NDKRelaySubscription.swift:264-277`), and `NDKSubscriptionCoordinator.handleClosed` (`DataSource/NDKSubscriptionCoordinator.swift:483-495`) are unreachable. A user-banned, rate-limited or auth-required subscription stays "active" forever, and the relay's CLOSED reason is lost. Fix: add a `closed(subscriptionId, message)` case to `NostrMessage` and a corresponding parse branch, then wire it through `NDKRelay.routeMessage`.

- **Two parallel reconnect schedulers race after a disconnect.** — `Sources/NDKSwiftCore/Relay/NDKRelayConnection.swift:586-609` and `Sources/NDKSwiftCore/Models/NDKRelay.swift:703-729` — When the WebSocket fails, `NDKRelayConnection.handleConnectionError` calls `scheduleReconnection()` which schedules the **actor's own `connect()`** through `retryPolicy.scheduleRetry` (rebuilds the URLSession task on the same actor). Simultaneously the delegate fires `relayConnectionDidDisconnect(_:error:)` which `NDKRelay` handles via `handleConnectionFailure`, scheduling a separate `Task.sleep` + `self.connect()` on `NDKRelay` (line 718) that constructs a **brand new `NDKRelayConnection`**. The two timelines can produce duplicate sockets, dueling REQ floods, and orphaned actors. Fix: pick one owner. The recommended pattern is to let `NDKRelay` own reconnection and remove `NDKRelayConnection.scheduleReconnection` entirely.

- **`NDKRelay.connect()` leaks the previous `NDKRelayConnection` and its tasks on every reconnect.** — `Sources/NDKSwiftCore/Models/NDKRelay.swift:644-674` — Line 665 unconditionally allocates a new `NDKRelayConnection`; line 666 replaces it in the state actor via `setConnection`. There is no `await currentConnection?.disconnect()` before the swap. The old actor still holds `healthCheckTask`, `stateMonitorTask`, the in-flight `receiveMessages()` detached task, and a non-cancelled `retryPolicy` (which itself holds a `Timer.scheduledTimer`, see Medium below). Because these Tasks retain `self` strongly, deinit never fires and the actor is permanently alive — every reconnect compounds the leak. Fix: `await stateActor.getConnection()?.disconnect()` before allocating a replacement.

- **`NDKRelay.disconnect()` no-ops while the relay is authenticated or in any auth-related state.** — `Sources/NDKSwiftCore/Models/NDKRelay.swift:680-684` — `guard currentState == .connected || currentState == .connecting else { return }` silently drops disconnect calls when the relay state is `.authenticated`, `.authRequired`, `.authenticating`, or `.failed`. That means an authenticated NIP-42 relay cannot be disconnected by the user, and a `.failed` relay's pending reconnect Task (scheduled in `handleConnectionFailure`) is never cancelled. Fix: include all "live or transitional" states in the guard (or invert: only skip if already `.disconnected`/`.disconnecting`).

## High

- **`NDKFilterFingerprint.toFingerprint()` uses non-deterministic `Array.hashValue` for grouping keys.** — `Sources/NDKSwiftCore/Subscription/NDKFilterFingerprint.swift:22, 26, 30, 42-44` — Swift's `Hasher` is seeded randomly per process, so `["alice"].sorted().hashValue` differs every run. Within a single process this still groups correctly, but: (1) any persistence of fingerprints (cache `getLastFetchTime(for:)`, debug logs, replay across cold starts) will be invalidated on restart; (2) two NDK instances inside the same process — or a forked extension — can disagree; (3) fingerprints are compared as keys in `relayIdToFingerprint` (`DataSource/NDKSubscriptionCoordinator.swift:12`) and `fingerprintSubscriptions` (line 11). Use a deterministic hash (SHA-256 of a canonical string), matching the pattern already in `NDKFilter.fingerprint` at `Models/NDKFilter.swift:476-482`.

- **`NDKNostrRPC.sendRequest(..., handler:)` registers the response continuation AFTER the request is sent — lost-update race.** — `Sources/NDKSwiftCore/RPC/NDKNostrRPC.swift:172-190` — `sendRequestInternal` (line 175) publishes the event to the relay and returns. Only afterwards a `Task` is spawned which calls `waitForResponse(id:)` (line 183) that finally inserts into `pendingRequests`. A fast remote signer can deliver the encrypted response event before the inserting Task runs, and `parseEvent` at line 112 (`if let continuation = pendingRequests[id]`) silently drops the response — the handler is never called and there is no timeout because no continuation was stored. Fix: register the continuation in `pendingRequests` before calling `sendRequestInternal`, exactly as the throwing variant at line 196-216 does.

- **`RetryPolicy.execute` truncates sub-second delays to zero.** — `Sources/NDKSwiftCore/Utils/RetryPolicy.swift:177` — `try await Task.sleep(nanoseconds: UInt64(delay) * TimeConstants.nanosecondsPerSecond)`. `delay` is a `TimeInterval` (Double). `UInt64(0.5)` is `0`. Any retry delay below 1s becomes an immediate retry. Affects `rpcRequest` config (`initialDelay: 0.5`) and any jitter that pushes a base delay under 1s. Fix: `UInt64(delay * Double(TimeConstants.nanosecondsPerSecond))`, matching the pattern used everywhere else (e.g. `NDKRelayConnection.swift:343`).

- **`SubscriptionSwapManager.filtersEqual` ignores most filter fields.** — `Sources/NDKSwiftCore/Core/Subscription/SubscriptionSwapManager.swift:98-105` — Compares only `kinds`, `authors`, `tags`, `since`, `until`. It silently considers two filters identical if `ids`, `events`, `pubkeys`, or `limit` changed. The swap path at line 70 (`guard !filtersEqual(...) else { return }`) will skip a needed swap. Fix: compare by `NDKFilter` equality, which is already `Equatable` (`Models/NDKFilter.swift:10`).

- **`EOSETracker.trackEOSE` drops EOSE from any unexpected relay, including relays added through replay where order matters.** — `Sources/NDKSwiftCore/DataSource/EOSETracker.swift:51-65` — The guard `expectedRelays.contains(relay)` returns early and logs a warning. If an event arrives from a relay before `setExpectedRelays`/`addExpectedRelay` records it (e.g., when a new relay is added concurrently with `applyOutboxStrategy`), its EOSE is permanently lost, so `allRelaysEOSEd()` may never become true and `closeOnEose` subscriptions hang. Fix: when receiving an EOSE from a non-expected relay, log and add it to `eosesSeen` keyed against an extended `expectedRelays`, or defer until `addExpectedRelay` catches up.

- **`NDKRelayConnection.send(_ json:)` re-parses every outbound JSON for logging purposes on the hot path.** — `Sources/NDKSwiftCore/Relay/NDKRelayConnection.swift:373-380` — On every REQ/EVENT/CLOSE, the JSON is parsed via `NostrMessage.parse(from: json)` solely to log it, even when log level is below trace/debug. For a busy app this is significant CPU on the actor and serialises all sends behind the parser. Fix: gate behind log-level check, or pass the structured `NostrMessage` directly from `send(_ message: NostrMessage)`.

- **`HintIndex.evictIfNeeded` is O(N log N) per insertion past the cap and rebuilds the full set every time.** — `Sources/NDKSwiftCore/RelayIntelligence/HintIndex/HintIndex.swift:265-356` — Once `totalEntries > maxSize`, every new `recordHint` call enumerates all three dictionaries, allocates an `EntryRef` for every entry, sorts them, and rewrites entries. With `maxSize = 10000` this is several megabytes of allocation per hint write. Worst case is a busy subscription firing many `recordEventObservation` calls per event delivery (`NDKSubscriptionRequirement.swift:381`). Fix: track a heap/index of `recordedAt` keyed by `(table, key, index)` or use a true LRU map.

- **`NDKNostrRPC.parseEvent` mutates `encryptionScheme` based on a successful decrypt with the "other" scheme — globally for the actor.** — `Sources/NDKSwiftCore/RPC/NDKNostrRPC.swift:68-75` — After a single fallback decrypt succeeds, future encrypts to **other** signers also use the swapped scheme. A legitimate NIP-44 peer responding once with an NIP-04 reply (e.g. a different remote signer pinging the same NDK) would permanently downgrade the entire RPC channel's encryption. Fix: scope the scheme per-peer pubkey, not per-actor.

## Medium

- **`RetryPolicy` uses `Timer.scheduledTimer` which silently fails off the main RunLoop.** — `Sources/NDKSwiftCore/Utils/RetryPolicy.swift:117-134` — `Timer.scheduledTimer(withTimeInterval:...)` adds the timer to the current RunLoop. `NDKRelayConnection.scheduleReconnection` calls it inside an actor-isolated method (which doesn't have a running RunLoop on its executor). The timer may never fire; even when it does, the user-visible reconnect delay is unpredictable. Replace with `Task.sleep`.

- **`RetryPolicy` for `relayConnection` has `maxAttempts: nil` and uses a per-relay shared `Bool isRetrying`** — `Sources/NDKSwiftCore/Utils/RetryPolicy.swift:21-27, 124-129` — Permanently-down relays will retry forever. Combined with the dual reconnect path (see Critical #2) and the eviction logic in `NDKPool.evictIdleRelays`, a connection that fails to authenticate can keep scheduling itself indefinitely. Add a cap.

- **`NDKSubscriptionGroupingMetrics.groupSizes` is an unbounded `[Int]`.** — `Sources/NDKSwiftCore/Relay/NDKSubscriptionGroupingMetrics.swift:21, 48-50, 84-85` — Every REQ ever sent pushes an integer; never trimmed. The `getSnapshot()` reads `Double(groupSizes.reduce(0, +)) / Double(groupSizes.count)` over the entire history. Memory grows linearly with subscription count over the process lifetime. Fix: keep a running sum/count or a bounded ring buffer.

- **`NDKSubscriptionCoordinator.handleEvent` does no local filter validation before delivering to observers.** — `Sources/NDKSwiftCore/DataSource/NDKSubscriptionCoordinator.swift:445-459` — A relay that returns events not matching the requested filter (malicious, or due to filter merging in `NDKRelaySubscription.compileFilters` `Relay/NDKRelaySubscription.swift:194-230` where multiple grouped filters share a REQ) will fan its extra events out to all grouped subscribers, even those whose individual filters reject them. `NDKSubscriptionRequirement.handleNetworkEvent` does filter (`DataSource/NDKSubscriptionRequirement.swift:392`), but the coordinator-level `onEvent` callback fires first without filtering. Defence-in-depth fix: validate `filters.contains { $0.matches(event:) }` at line 454.

- **`NDKRelayConnection.publishEvent` returns "Event already being published" if a caller publishes the same `event.id` twice — this can mis-fire on legitimate replays.** — `Sources/NDKSwiftCore/Relay/NDKRelayConnection.swift:328-359` — Authentication retries (`Core/NDK.swift:858 retryFailedPublishesForRelay`) may legitimately re-publish the same event after auth succeeds. With another publish to the same relay in-flight, the second attempt fails synthetically with `publishFailed("Event already being published")` instead of waiting for the first OK. Fix: dedupe by attaching the new continuation to the existing pending OK (multi-waiter), or short-circuit with `.success(true)` if a recent OK exists.

- **`NDKNostrRPC.parseEvent` partial-success path may drop the success response.** — `Sources/NDKSwiftCore/RPC/NDKNostrRPC.swift:111-124` — Comment says "Error response - log but keep waiting for potential success", but the continuation isn't resumed *and* the timeout task may have already fired between receiving the error and a future success, leaving the success response handler to call `pendingRequests[id]` which has been removed by `handleTimeout`. A second response then logs nothing. Track this state explicitly (`pendingRequests` entries with `lastErrorMessage`), and resume on first non-error or on timeout with the last error.

- **`NDKRelayCoverageTracker.clearRelay` does not remove that relay from `eventFirstDelivery`, but the comment admits this leaves dangling state.** — `Sources/NDKSwiftCore/RelayIntelligence/NDKRelayCoverageTracker.swift:136-140` — Subsequent calls to `recordDelivery` for those events will count any later delivery as "duplicate" (since `eventFirstDelivery[eventId] != nil`), permanently skewing `firstDeliveryCount` on the relay that actually re-delivered first. Either purge or persist the "this was first" decision elsewhere.

- **`NDKSubscriptionManager.startPeriodicCleanup` is a do-nothing infinite loop.** — `Sources/NDKSwiftCore/DataSource/NDKSubscriptionManager.swift:40-47` — Sleeps an hour, wakes, sleeps again, never does anything. Either remove or implement.

- **`NDKSubscriptionRequirement` retains `seenEventIds` for the lifetime of the requirement with no eviction.** — `Sources/NDKSwiftCore/DataSource/NDKSubscriptionRequirement.swift:17, 348, 370, 487` — For long-running (`!closeOnEose`) subscriptions like a global timeline, this is an unbounded `Set<EventID>` (string IDs). Add a max-size LRU or a Bloom filter for older IDs.

- **`NDKRelayConnection.connect()` allows multiple pending `connectionContinuations` to be enqueued, but if the spawning Task at line 165 throws, only the latest continuation is failed.** — `Sources/NDKSwiftCore/Relay/NDKRelayConnection.swift:160-193` — Recovery via `resumeAllContinuations` (line 614-625) is invoked on success/failure of `_connect`, but a thrown error inside `withCheckedThrowingContinuation` doesn't propagate to `resumeAllContinuations` automatically. The catch at line 169 only catches the local continuation's resumed throw — other queued waiters remain orphaned if the path takes the `isInitialConnection` branch (line 179) that re-throws without scheduling reconnect. Trace the paths to confirm all waiters are resumed.

## Low

- **`NDKRelay.handleConnectionFailure` reads `delay` from `getReconnectDelay()`, computes `actualDelay = min(delay, ...)`, then mutates `delay * 2` — but the new delay is written *before* `actualDelay` is consumed by the sleep.** — `Sources/NDKSwiftCore/Models/NDKRelay.swift:714-719` — The next iteration sees `delay * 2` but the current `actualDelay` is `min(delay, max)` (the pre-doubling value), so the math works — yet doubling happens before the sleep starts. Reads correctly today; brittle if anyone refactors the read/write order. Make atomicity explicit.

- **`NDKRelaySubscriptionManager.handleRelayReconnection` re-executes any group whose status is `< .closed` via `isActive()` — but `isActive()` is defined twice with different semantics.** — `Sources/NDKSwiftCore/Relay/NDKRelaySubscription.swift:73-74` (`status == .running`) vs. `Sources/NDKSwiftCore/Relay/NDKRelaySubscription.swift:320-322` (`status < .closed`). The first is the protocol-level definition, the second is an extension in `// MARK: - Testing Support`. The actual call in `Relay/NDKRelaySubscriptionManager.swift:153` resolves to the testing-support version because of Swift's overload resolution rules — and that's only via a `where` clause on `await group.isActive()`. Hard to reason about; consolidate the naming.

- **`NDKPool.appRelays` is a synchronous computed property reading actor-isolated state.** — `Sources/NDKSwiftCore/Core/Managers/NDKPool.swift:502-506` — Declared `public var appRelays: [NDKRelay] { ... }`. Because `NDKPool` is an actor, accessing this from outside requires `await`. Fine, but the property as written walks `relayMap.values.filter` synchronously; combined with `appRelayUrls`, two sources of truth that can drift. Use a single computation.

- **`NDKConnectionMonitor`'s NSObjectProtocol observers are stored on actor state but `removeObserver` is called from `deinit` outside actor isolation.** — `Sources/NDKSwiftCore/Relay/NDKConnectionMonitor.swift:189-197` — Comment claims Swift 5.9 actor deinit runs on the actor executor; that is only true on certain compile flags. Cross-version safety is not guaranteed.

- **`NDKRelay.observeConnectionState` calls the observer twice on registration in some paths.** — `Sources/NDKSwiftCore/Models/NDKRelay.swift:947-952` — Adds observer, then synchronously invokes it with current state. But `addStateObserver` triggers no callback (good), and the explicit observer call uses the snapshot at line 950. If the state changes between line 948 and line 950, a different value is delivered out of order to that observer compared to the others. Order matters less than determinism; document or fix.

- **`NDKRelaySubscription.close()` does not finish or notify `NDKSubscriptionCoordinator.handleClosed`** — `Sources/NDKSwiftCore/Relay/NDKRelaySubscription.swift:280-301` — Group is closed but its members' `handleClosed` is NOT invoked here (only `handleEvent`/`handleEOSE`). Combined with Critical #1 (CLOSED never received) this means coordinators are never told their subscription is gone unless EOSE arrives.

- **`NDKNetworkMonitor.handlePathUpdate` mismatches "expensive" change with "type change".** — `Sources/NDKSwiftCore/Relay/NDKNetworkMonitor.swift:115-128` — `wasExpensive != isNowExpensive` triggers a "type change" notification; this is technically a cost change, not a type change. Minor terminology bug.

- **`NDKConnectionErrorRateLimiter.shouldLogError` cleans up old records *before* checking the current error.** — `Sources/NDKSwiftCore/Relay/NDKConnectionErrorRateLimiter.swift:22-26` — The first error of a session immediately triggers the cleanup pass, which is fine, but the cleanup uses `now.timeIntervalSince(record.lastLogged)` — records older than 5 minutes get evicted even if their error count was meaningful. Document/intent unclear.

- **`NDKRelaySubscription.scheduleExecution` `(atMost, atLeast)` branch is missing.** — `Sources/NDKSwiftCore/Relay/NDKRelaySubscription.swift:78-105` — `switch (existingDelayType, delayType)` is exhaustive (4 cases listed) but the comment-vs-code mismatch is suspicious: `(.atLeast, .atLeast)` extends, `(.atLeast, .atMost)` and `(.atMost, .atMost)` reduce, `(.atMost, .atLeast)` is treated like a reduction but the comment says "Keep the at-most constraint if fire time is within the at-least delay". A careful pass against ndk-core semantics is warranted.

## Observations

- **Many critical relay/subscription tests are in `Tests/NDKSwiftTests/DisabledTests/`.** — Files including `NDKRelayConnectionTests.swift`, `NDKRelayOKMessageTests.swift`, `NDKRelayAuthenticationFlowTests.swift`, `NDKRelaySubscriptionGroupTests.swift`, `CustomSubscriptionIdTests.swift`, `SubscriptionReplayTests.swift`, `RelayConnectionRaceConditionTests.swift`, `EOSECollectTests.swift`, `SubscriptionGroupingMetricsTests.swift`, `GroupedSubscriptionIsolationTests.swift`, `MultipleObserversTests.swift`, `EnhancedRequirementsTests.swift`, `BroadFilterReactiveTest.swift` are disabled. The first one references an outdated delegate signature (`relayConnection(_:didReceiveMessage:)` instead of `…byteCount:`), confirming these reflect known broken behavior or API drift, not just temporary skips. Owning the relay/subscription domain currently means there's no automated coverage of REQ id collisions, OK message handling, race conditions on connect/disconnect, or EOSE aggregation.

- **Per-relay subscription tracking is duplicated three ways**: `RelayStateActor.activeSubscriptions: [String: NDKRelaySubscriptionInfo]` (`Models/NDKRelay.swift:157`), `NDKRelaySubscriptionManager.subscriptionGroups` + `subscriptionIdToGroup` (`Relay/NDKRelaySubscriptionManager.swift:12-14`), and `InternalSubscriptionManager.relayToSubscriptions` (`DataSource/NDKSubscriptionCoordinator.swift:15`). Each is updated from a different code path (`trackSubscription`, `trackGroupSubscriptionId`, `updateRelayAssociation`), making "is this REQ live on this relay?" answer non-trivial.

- **Two implementations of subscription fingerprinting exist with overlapping but different rules**: `NDKFilterGrouping.filterFingerprint` (`Relay/NDKFilterGrouping.swift:17-50`) is **key-name-only** (groups together filters with the same shape but different values) and prefixes with `+` for `closeOnEose`; `NDKFilterFingerprint.toFingerprint` (`Subscription/NDKFilterFingerprint.swift:16-53`) includes hashed values to disambiguate. They are used for distinct purposes (relay-level grouping vs. coordinator-level routing) but the divergence is undocumented and confusing.

- **`NDKRelay.send` updates stats but the actor-internal `NDKRelayConnection` ALSO increments its own `messagesSent` counter** (`Relay/NDKRelayConnection.swift:394`). Two counters, one source-of-truth, drifting on retry.

- **NIP-11 fetch swallows all errors silently** unless `ndk.debugMode` is true (`Models/NDKRelay.swift:752-757`). Connection establishment proceeds even when relay info is unavailable, which is fine; just note that limitations declared by the relay (e.g. `maxFilters`, `maxLimit`, `authRequired`) are never used to constrain outbound REQs.

- **`NDKPool.removeRelay` does not cancel in-flight `NDKSubscription`s pinned to that relay's URL** before disconnecting. They sit in `NDKSubscriptionCoordinator.activeRelays` and continue to receive zero events. Cleanup is implicit via stream finish.

- **`NDKNostrRPC.attemptDirectSend` swallows individual relay failures** (`RPC/NDKNostrRPC.swift:249-262`), but the parent `sendRequestInternal` already returned successfully — the user only sees a generic timeout if all sends failed. Worth surfacing per-relay outcomes.
